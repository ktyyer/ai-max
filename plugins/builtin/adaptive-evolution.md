# Adaptive Evolution - 自主演进闭环

> 把「改代码」升级为「可度量的持续进化」

## 触发条件

- 任务包含“迭代”“演进”“持续优化”“评估”“基准”“回归”
- 任务目标是“让项目长期变好”，而不是一次性修补
- 或：需要建立自动化质量门禁（CI / 本地）

---

## 借鉴的开源模式（可直接执行）

1. **Issue 驱动闭环**（OpenHands / SWE-agent）
   - 从“问题定义”开始，而不是直接改代码
   - 每轮都产出可验证变更（补丁 + 验证结果）
2. **基准优先**（SWE-bench）
   - 先定义评估集，再做优化，避免“感觉变好”
3. **仓库地图最小上下文**（Aider）
   - 先定位关键文件和调用链，减少盲改
4. **状态化执行 + 人类门禁**（LangGraph）
   - 长流程按阶段推进，关键节点可人工确认
5. **评估即门禁**（Promptfoo / Continue）
   - 把质量标准固化为可重复检查，而非口头约定
6. **失败重试与模型回退**（LiteLLM）
   - 单次失败不终止，按策略重试并降级

---

## 自主演进流程（7 步）

### Step 1: 定义迭代目标

```markdown
目标 = 业务指标 + 工程指标 + 风险边界

示例：
- 业务：接口 P95 延迟下降 30%
- 工程：测试稳定性 >= 95%
- 风险：禁止引入破坏性 API 变更
```

### Step 2: 构建项目基线

- 收集当前指标：测试通过率、覆盖率、构建时长、错误率
- 读取项目已有规范：lint/formatter/test/architecture 约束
- 生成“本轮前状态”快照，后续对比必须基于快照

### Step 3: 生成最小改动方案

- 使用仓库地图定位关键路径（入口、核心模块、测试）
- 先提出最小补丁，不一次性做大改
- 对每个补丁给出“预期收益 + 风险 + 回滚点”

### Step 4: 执行验证矩阵

```yaml
verification_matrix:
  required:
    - compile_or_build
    - unit_tests
    - integration_tests
    - lint_and_typecheck
  optional:
    - e2e_tests
    - security_scan
    - llm_eval_suite
```

### Step 5: 评分与门禁

```yaml
gates:
  tests_pass_rate: ">= 100%"
  coverage_delta: ">= 0"
  regression: "0 critical regressions"
  perf_target: "达到本轮目标或说明未达成原因"
```

- 通过：进入下一轮迭代或收敛
- 不通过：进入 Step 6 失败恢复

### Step 6: 失败恢复（最多 3 轮）

1. 识别失败类型：用例回归 / 性能未达标 / 风格不一致 / 误改
2. 先收敛上下文：缩小变更面，定位根因
3. 重试策略：
   - 第 1 轮：同方案小修补
   - 第 2 轮：替代实现
   - 第 3 轮：回退到上一个稳定点并输出人工决策建议

### Step 7: 沉淀进化记忆

- 记录成功模式：有效策略、可复用片段、触发条件
- 记录失败模式：反例、排查路径、规避策略
- 把“本轮经验”转成下一轮默认约束

---

## 核心原则

1. **先评估再优化** - 没有基线就不做“优化结论”
2. **小步快跑** - 每轮必须可验证、可回退
3. **项目优先** - 始终先遵循项目既有代码风格和约束
4. **失败可恢复** - 任何自动化流程都必须有降级路径
